# Learning Plan: Manual QA to AI-Native AQA Engineer

**Duration:** about 17 weeks at ~6–7 h/week (mobile track adds ~1–2 weeks of load)
**Starting point:** manual QA, near-zero software development tooling knowledge
**Mentor:** available weekly

## 1. Principles

1. **Do not learn what an agent already does well enough.** She does not write or review application/test code line by line. Code is generated by agents.
2. **Verification rests on mechanisms, not on reading code.** Tests of the tests, automated gates, agent self-checks and independent review agents.
3. **Literacy, not fear.** She is comfortable opening files and logs, knows the concepts and the environment, and can direct coding agents.
4. **Terminal-first.** Work happens in the terminal and with CLIs, as agents do.
5. **Her edge is judgment:** test design, risk, ambiguity, diagnosis. Agents are weak here.
6. **Every phase ends with something built, not something watched.**

## 2. Skill map

**Deep expertise (she owns it):**
1. Agent management and workflow design
2. Verification layers (making agents find their own issues, avoiding overcomplicated solutions)
3. Test strategy under ambiguity
4. Failure and flake diagnosis

**Literacy only (understands, directs, does not master):**
- Terminal, shell, CLIs
- How software runs: compile/interpret, runtimes, dependencies, paradigms (names and shapes)
- Virtualization, containers, cloud basics (AQA-relevant only)
- HTTP, DOM, git concepts
- Mobile AQA toolsets: platform concepts, emulators/simulators, Appium/Maestro-style frameworks, device clouds
- LLM evals, data/secrets/cost governance

**Out of scope:** writing or reviewing application code, native mobile app development (Swift/Kotlin), design patterns, system architecture, algorithms and data structures, Kubernetes/IaC authoring.

## 3. Tooling constraints

- Claude Code (primary agent), open-source IDE (e.g. VS Code or a fork)
- Open-source orchestrators for parallel agents/subagents (use the approved one)
- Allowlisted MCPs only (confirm whether Playwright MCP is on the list; otherwise Claude Code drives the Playwright CLI)
- CLIs: `claude`, `gh`, `git`, `docker`, `curl`, `jq`, package manager, test runner, cloud CLI
- Mobile: Android SDK command-line tools (`adb`, `emulator`), Xcode command-line tools (`xcrun simctl`), Appium and/or Maestro, and a mobile MCP if allowlisted

All practice uses only approved tools so learning transfers directly to work.

## 5. Phases

### Phase 0: Setup and orientation (Week 1)
- Install Claude Code, IDE, `gh`, approved MCPs. The agent performs the installation; she asks it to explain each step.
- Vocabulary: repo, branch, dependency, environment variable, process, port, log.
- Practice opening files, folders and logs without needing to understand every line.
- **Done when:** she can ask the agent "what is this project and how do I run it?" and sanity-check the answer.

### Phase 1: Directing a coding agent (Weeks 2–4)
- **How agents work:** context limits, tool use, permissions, failure modes (looping, scope drift, hallucination).
- **Task design:** decomposing work, specs, acceptance criteria, a done-definition the agent can check itself.
- **Context engineering:** `CLAUDE.md`, skills, reusable prompts, "prefer the smallest change" rules.
- **Interaction habits:** plan mode, small steps, asking the agent to explain its choices, when to restart a session.
- **Drill:** mentor gives a vague ticket; she turns it into a spec and the agent builds from it.
- **Done when:** she gets a working feature from a vague ask with a clear spec and no more than two redirections.

### Phase 2: Building the verification layer (Weeks 5–8)
- **Self-checking loops:** the agent runs tests, linter and type-checker before reporting done (hooks, project rules).
- **Test-the-tests:** mutation testing, planted bugs, critical use of coverage, diff-based gates that catch weakened or deleted assertions.
- **Independent verification:** a second agent or subagent reviews the first one's work against the spec, not the code.
- **CI gates:** required checks, flake detection, artifacts the agent can read (traces, screenshots, logs).
- **Simplicity guardrails:** diff/file size limits, "no new dependencies without approval", complexity linters.
- **Project:** a Playwright/pytest suite for a demo app, built entirely by agents under her verification layer.
- **Done when:** she can show a planted defect the suite caught, a weakened test the gates caught, and one the layer missed, plus the fix she made to the layer.

### Phase 3: Strategy and ambiguity (Weeks 7–10, overlapping)
- Risk-based coverage, what to automate, test pyramid.
- Requirement analysis: finding gaps, asking clarifying questions, recording assumptions.
- Agent-assisted exploratory testing and test-design generation, which she prunes and prioritizes.
- **Drill:** mentor supplies an ambiguous feature description with conflicting requirements. She produces a strategy and a list of questions, then compares it to the agent's.
- **Done when:** she can defend what is and is not automated, and why.

### Phase 4: Failure and flake diagnosis (Weeks 10–12)
- Reading CI logs, traces and timing data (not code) to localize failures.
- Distinguishing product bug, test bug, environment issue and flake.
- Making the agent investigate with evidence; rejecting fixes that add sleeps or retries without a cause.
- **Drill:** 5 seeded failures. She directs an agent to diagnose each and judges whether the diagnosis is real.
- **Done when:** she correctly classifies all 5 and can justify each classification with evidence.

### Phase 5: Orchestration and capstone (Weeks 12–17)
- Parallel agents and subagents with the approved orchestrator; handoffs between agents.
- AI-assisted triage and bug-report drafting with her sign-off.
- Literacy-level coverage of LLM evals and of data, secrets and cost governance.
- **Capstone:** an end-to-end workflow from vague requirement to spec, agent-built tests, verification layer, CI, and a triaged failure report. It includes a small mobile suite (Track M) on an emulator/simulator in CI. She documents the decisions she made and why.

## 6. Track T: Terminal-first and CS literacy

### T1: Terminal and shell (Weeks 1–3)
- **Navigation and files:** `cd`, `ls`, `pwd`, `cat`, `less`, `cp`, `mv`, `rm` (and why it is dangerous), absolute vs relative paths.
- **Searching and filtering:** `grep`, `find`, `head`, `tail -f`, pipes, redirects (the tools for reading logs).
- **Shell concepts:** environment variables and `PATH`, exit codes, stdin/stdout/stderr, processes, background jobs and signals, file permissions, `.env` and dotfiles.
- **Scripts:** what a shell script is and how to run one (agent writes them).
- **CLIs:** `claude`, `gh`, `git`, package manager, test runner, `curl`, `jq`, `docker`, cloud CLI.
- **Habit:** read a command before approving it, especially anything with `rm`, `sudo`, `curl | sh` or `--force`.
- **Done when:** she can find the failing line in a 10,000-line log from the terminal and explain a command the agent proposes.

### T2: How software runs (Weeks 3–5)
- **Compiled vs interpreted vs JIT:** what a build step is and why some projects have one.
- **Runtimes and dependencies:** Python, Node and the JVM at concept level, packages, lockfiles, version pinning, virtual environments ("works on my machine").
- **Paradigms (names and shapes only):** procedural, object-oriented, functional, event-driven, async, and why async tests behave differently.
- **Core ideas:** static vs dynamic types, exceptions, state, side effects, why determinism matters for tests.
- **Data formats:** JSON, YAML, env files, config layers.
- **Concurrency basics:** processes vs threads, race conditions, timeouts (the source of flakes).
- **Done when:** she can explain to an agent, in plain words, why a test passes locally and fails in CI.

### T3: Environments, virtualization and cloud (Weeks 6–9)
- **Virtualization:** VMs vs containers, images vs containers, Docker basics (`build`, `run`, `ps`, `logs`, `exec`), Compose for multi-service test environments.
- **Environment parity:** why CI runs in containers; how local and CI differ.
- **Networking for testers:** localhost, ports, DNS, HTTP vs HTTPS, proxies, why a service is unreachable.
- **Cloud basics (AQA-relevant only):** regions, compute, storage, managed services at concept level; ephemeral test environments; secrets managers; IAM and least privilege; cost drivers.
- **CI runners:** hosted vs self-hosted, caching, artifacts, parallel jobs.
- **Done when:** she can spin up the demo app and its dependencies in containers with an agent and reason about why a CI job is slow or red.

## 7. Track M: Mobile AQA toolsets (Weeks 9–13)

Goal: she knows the mobile landscape well enough to choose a toolset, set it up with an agent, and direct agents on mobile tests. She does not learn to build native apps.

**M1: Mobile platform concepts**
- **App types:** native, hybrid, web/PWA, cross-platform (React Native, Flutter), and how that changes what can be automated.
- **Artifacts:** APK/AAB vs IPA, debug vs release builds, app signing and provisioning at concept level, and where test builds come from.
- **Platform differences:** Android vs iOS, OS version and device fragmentation, screen sizes and densities.
- **Mobile-specific risk areas** (feeds her test strategy): permissions, interruptions (calls, notifications), backgrounding, network changes and offline mode, gestures, deep links, push notifications, upgrades and data migration, battery and performance, accessibility.

**M2: Devices and environments**
- **Emulators and simulators:** Android Virtual Devices and iOS Simulators, what they can and cannot reproduce, and real-device vs emulator trade-offs.
- **CLI tooling:** `adb` (install, logs via `logcat`, screenshots, screen recording), `xcrun simctl`, and reading crash logs.
- **Device clouds:** BrowserStack, Sauce Labs and similar, what they offer, cost drivers, and how CI connects to them. Use only what is approved.
- **Local vs CI:** why mobile CI is slower and flakier (emulator boot times, macOS runners for iOS).

**M3: Automation frameworks (know the options, direct the agent)**

| Tool | What she should know |
|---|---|
| Appium | The cross-platform standard. WebDriver-based, drivers per platform, server plus client architecture, flexible but slower and flakier. |
| Maestro | YAML flows, simple setup, fast to write, good fit for agents and for smoke tests. |
| Espresso (Android) and XCUITest (iOS) | Native, fast and stable, but platform-specific and tied to app code and build. |
| Detox (React Native) and Flutter integration tests | Framework-specific, relevant if the product uses them. |
| Playwright mobile emulation | Not real mobile. Good for responsive web only. |

- **Locators:** accessibility IDs vs XPath, and why developer cooperation on IDs matters for stability.
- **Mobile MCPs:** agent control of an emulator or device through an allowlisted MCP (for exploratory testing and screenshot-based checks), plus the risks: slow, screenshot-driven, non-deterministic.
- **Selection criteria:** team skills, platforms, app type, CI constraints, flake tolerance, and maintenance cost.

**M4: Verification layer on mobile**
- Apply Phase 2 ideas: mutation or planted bugs in the app, flake detection on emulators, artifacts the agent can read (screen recordings, `logcat`, screenshots), and simplicity guardrails.
- Mobile-specific diagnosis: tell app bug, test bug, device/emulator issue, OS-version issue and network issue apart.

**Project:** use a public demo app (an open-source sample for Android and/or iOS). With agents, build a small smoke suite in Maestro or Appium, run it on an emulator/simulator, and wire it into CI.

**Done when:**
- she can explain to a stakeholder which mobile framework fits their product, and why;
- the agent-built suite runs from the terminal and in CI;
- she can classify a seeded mobile failure (emulator boot problem, missing permission, stale locator, real bug) with evidence from logs.

## 8. Mentor rhythm

- **Weekly, 45 min:** one planted-flaw drill, such as a vague ticket, a weakened test, a plausible but wrong diagnosis, or an over-engineered solution.
- **Phase-end review:** she walks through her workflow and decisions, not code.
- **Terminal drills:**
  - "Explain this command before you run it" with a hidden risk in it.
  - A broken environment (wrong Python version, missing env var, port in use). She names the category before the agent fixes it.
  - A log haystack: find the root cause using only terminal tools.
  - A "works locally, fails in CI" case that traces to an environment difference.
- **Mobile drills:**
  - Pick a framework for a described product (native iOS and Android, React Native, or hybrid) and defend the choice.
  - Seeded failure: an emulator that won't boot, a missing permission prompt, a stale locator, or a real bug. She classifies it from `adb logcat` or the recording.

## 9. Portfolio

A public repo containing the Phase 2 suite, a mobile smoke suite and the capstone. The README documents the verification layer, the agent configuration, and the failure cases the layer caught or missed.

## 10. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Rubber-stamping agent output | Planted-flaw drills; mechanism-based gates that do not rely on her attention. |
| Agent tooling churn | Focus on durable skills: verification, spec writing, diagnosis, strategy. |
| Agent loops or gets stuck | Concept literacy (T1–T3) lets her recognize the situation and redirect or restart. |
| Overcomplicated agent solutions | Simplicity guardrails and "smallest change" rules in `CLAUDE.md`. |
| Unsafe commands or leaked secrets | Terminal habit of reading commands first; secrets checklist; allowlisted tools only. |
| Hiring managers asking if she can read code | Show the verification layer working with real caught and missed defects. If a target employer insists, add a short code-reading module. |
| Motivation dip around Weeks 4–8 | A visible small win each week; mentor check-ins. |
| Mobile setup friction (SDKs, emulators, signing, macOS requirement for iOS) | Let the agent do the setup; start with Android if no Mac is available; use a device cloud if approved. |
| Mobile suites are slower and flakier | Keep the suite small and smoke-level; rely on artifacts (recordings, logs) for diagnosis. |
